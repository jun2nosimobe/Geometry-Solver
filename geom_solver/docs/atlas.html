01

パイプライン全体

1問につき EGraph::new() → 問題ファイルによる初期条件の投入 → BlackboardEngine によるタスクキュー駆動の定理マッチング、という流れ。探索が完全に手詰まる(Stall)たびにオンデマンド作図の回復フェーズへ落ち、それも尽きればMCTSに委ねる。

02

マッチングの中身(dfs_match)

MatchTask は1つの定理・1つの束縛状態を表し、優先度付きキューで管理される。TheoremDef.patterns を先頭から満たしていくバックトラック探索で、パターンの型(Identical / Connected / DefinedBy / 汎用)ごとに専用の列挙ロジックを持つ。

Identical(v1, v2)

両方未束縛なら型で絞った代表元へ自己束縛(RETE的に定理をまたいで共有キャッシュ済み)。

Connected(child, parent)

e-graphの subobjects を辿る接続判定。両方未束縛のジョインも型だけで決まるため共有キャッシュ済み。

DefinedBy(…, result)

親が揃っていれば memo の O(1) ルックアップ、無ければ一部の型(Angle/Direction/Scalar)はその場で構成 — この副作用性が §3 で扱う設計上の緊張点。

failed_paths

1タスク内の「この束縛状態はもう行き止まり」の記憶。EGraph::type_generation(型ごとの世代カウンタ)が変わらない限り、dfs_cap到達での再キュー間で持ち越せる。

UCB1バンディット

シードなし全探索タスクの優先度を、定理ごとの過去の成功率+探索ボーナスで決める。未試行の定理は常に一度は試す。

4つのゲートウェイ

create_entity / merge_entities / link_logical_incidence / insert_memo。e-graphの生の構造を書き換える経路をここに集約し、type_generation の更新漏れを構造的に防いでいる。

schedule_matcher_task の二重チェックバグ修正

reverted
プロファイリング中に、シード済みタスクのポップ数が常にゼロという事実を発見。apply_conclusionsがFact発行前にself.factsへpush済みのため、run_step側の「二重登録ならschedule_matcher_taskを呼ばない」という判定が常にtrueになり、シード付き再マッチングが(Identical/Connectedとも)一度も起きていなかった。
結果: このバグを実際に直す(Identical単独/Connected単独/両方)実験をいずれも試したが、既存問題群の広範囲で重大な悪化を実測(simson 2〜3秒→35秒、miquel_quadrilateral→44.7秒、nine_point_full/bench_2010g1が新規に解けなくなる等)。UCB1・dfs_cap・熱ヒューリスティックが「シード付きタスクは実質発火しない」現状に暗黙に最適化されていたと考えられ、バグ修正自体は撤回。発見(バグの所在)はdocs/atlas.html兼コミットログに記録し、計測基盤だけを残した。
4回目の再挑戦(重複シード排除つき): 「同じ代表元ペアへの再シードが際限なく積み重なる」ことが悪化の主因ではないかと仮説を立て、(定理, パターン, 代表元ペア)単位で一度シードしたら二度と作らない重複排除(seeded_seen)を追加した上で再挑戦。結果はむしろ悪化: bench_2005ctstp1(25.7秒→解けたのに57秒でも未解決)、bench_2010g1(15.8秒→解けたのに46秒でも未解決)、bench_2011armog10p6(9.7秒→解けたのに10.3秒で未解決)など、31問題スイートの最初の数問だけで壊滅的な回帰。重複排除は「全く同じ代表元ペアへの再発火」は防げても、多数の円・直線が次々に自動統合される複雑な配置(bench_2005ctstp1等)では、事実が発見されるたびに常に新しい・別個の代表元ペアが生まれ続けるため、根本的な組み合わせ爆発の幅そのものは減らせないと判明。この4回目も撤回し、コードはバグ発見直後の状態(5d102de相当)に戻した。

TheoremDefの改善(uses索引化 + OrderNonStrict)

shipped
ユーザー目標「Simson級を1秒未満に」への対応。dfs_matchの探索木でどのパターンが実際に何回選ばれているかを数える一時計測(診断後に削除済み)を作り、simsonで最もdfs_call消費量が大きい「有向角の加法性」を実測で追跡した。(1) defined_by_valid_nodesの見落とし修正: DefinedByパターンの親変数が一部だけ束縛されている場合(例: AnglePair(D2,D3,Ang23)でD2だけ既知)、以前は「両方未束縛」と同じフルスキャンにフォールバックしていた。束縛済みの親のGeoEntity::uses(mergeを跨いで正しく引き継がれる「自分を親として参照する実体」の集合)で候補を絞り込むようにした――返す候補は下流が独立に再検証するsupersetで十分なので安全。(2) 新パターン種別Pattern::OrderNonStrict("≤"判定のOrder): 「2つの役割を丸ごと入れ替えても同じ結論になる」対称性を持つ定理(有向角の加法性の[D1,D2,D3]⇄[D4,D5,D6])向けに、厳密なOrder("<")では失われるD1==D4(方向共有、角度チェイス本来のユースケース)のケースを失わずに対称な重複探索だけを半分に間引く。数学的に正しさを検証済み。
結果: 診断の結果、有向角の加法性の真因は「Ang12≡Ang45とAng23≡Ang56という2つの独立な自己束縛が互いに無関係に全角度を列挙し掛け合わされる」ことだと判明し、この2つの修正だけではこの定理自体はほぼ変わらなかった(simson: 2.2s→2.1s)。しかしuses索引化はAnglePair以外のDefinedByパターン全般に効くため、31問題スイート全体では正誤を完全に保ったまま(全問題でbaselineと一致)、多くの問題で顕著な高速化を確認した: cyclic_quad 654ms→116ms、test_steiner 186ms→118ms、test_power_of_point 308ms→191ms、nine_point_full 27.0s→21.7s。Simson級を1秒未満にする目標にはまだ届いていない。
04

改善候補(優先度順)

検証を通じて分かった「まだ手が付いていない」項目。★は着手前に踏むべき前提条件を示す。

1

「二重自己束縛」定理を熱量駆動の起動に切り替える ★

TheoremDefの改善作業(uses索引化+OrderNonStrict)で診断用計測を使って追跡した結果、「有向角の加法性」(simsonの最大コスト要因、平均dfs_call消費量トップ)の真因が判明した: Ang12≡Ang45とAng23≡Ang56という2つの独立した自己束縛が、互いに無関係に全角度エンティティを列挙して掛け合わされている。これは「円周角の定理の逆」(コスト2位)でも同種の構造だと推測される。人間が幾何を解くときの流れ(ユーザー提案: 角度追跡→長さ・比の情報→構図の適用→角度追跡→…の反復で、その中で直前の角度追跡/長さ比に役立つ補助点・補助線を作る)を踏まえると、これらの定理は本来「今まさにhot(heat_bonusが高い/直前に証明された)角度」から芋づる式に辿るべきで、「グラフ上の全角度を無差別に自己束縛して総当たりする」のは人間の解き方と根本的に違う。全角度を無差別スキャンする代わりに、直近でheat_bonusが上がった(=直前の推論で使われた)角度を優先的に自己束縛候補にする、または後述#2の熱量ゲート付きシードで完全に置き換えることを検討する。
実測で特定済み中〜大規模
2

seeded task経路を「角度追跡系の定理だけ」に絞って再設計

schedule_matcher_taskによるシード付き再マッチングは、二重チェックバグにより実質的に一度も発火していなかった。単純に直す・重複排除を足す、いずれも全定理×全結論形式に無差別適用したため、既存問題群の広範囲で重大な悪化を招き4回撤回した。次に試すなら、無差別適用ではなく定理ごとにシード起動が必要かをタグ付けし、まず#1で特定した「二重自己束縛」定理(有向角の加法性・円周角の定理の逆)だけに絞ってシード駆動へ切り替える――対象がこの2〜3定理に絞られれば、他の20近い定理のシード無効化前提のUCB1/dfs_capチューニングを壊さずに済む可能性が高い。ユーザー提案の「角度追跡→長さ比→構図→角度追跡…」というフェーズ的な人間の解き方は、この絞り込みの基準(TheoremDefに角度追跡/長さ比/構図のカテゴリタグを持たせ、フェーズに応じてシード優先度を切り替える)としてそのまま使えそうで、単なるバグ修正の再挑戦より筋が良い。
要#1の知見スコープを絞れば低リスク化できる可能性
