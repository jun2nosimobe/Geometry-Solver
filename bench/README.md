# ベンチの回し方

検証は二段構え。**選抜で絞り込み、採用・コミット・記録の直前にだけ全問を回す。**
1手ごとに全問を回すと1回1時間近くかかり、試行が進まない(来歴 §04 #52)。

## 段1: 選抜(33問) ― 普段はこちら

```sh
bench/build.sh mychange          # いまの作業ツリーをビルドして bench/bin/mychange に置く
bench/quick.sh mychange          # 6設定 × 33問。基準(bench/res/qbase_*.tsv)と比べる
bench/quick.sh mychange "--my-flag"   # 全設定に足すフラグ
```

`bench/tier1.txt` は全44問から**どの設定でも一度も解けたことがない問題**を外したもの(2026-09-29 の基準更新で33問。基準を更新するたびに増減する)。
外した問題は毎回ステップ予算を使い切るだけで、仕事量の大半を食っていた。
基準の更新のたびに作り直す(下の手順)。解けた問題が増えたら選抜にも入る。

選抜が見るのは「解けている問題が壊れていないか」だけ。
**新しく解けるようになったのは捕まえられない**ので、採用の判断は必ず段2で取り直す。

## 段2: 確認(44問) ― 採用・コミット・記録の直前

```sh
bench/compare.sh mychange
```

## 基準の作り方と更新

`bench/res/<label>_<config>.tsv` が結果。基準は固定名で、
段2が `baseline_<config>.tsv`(44問)、段1が `qbase_<config>.tsv`(選抜の問題数)。

**変更を採用したら基準も更新する。** 忘れると、以後ずっと「採用済みの改善分だけ
良く見える」比較になってしまう。採用した版の44問の結果を `baseline_*` に写し、`tier1.txt`(どれかの設定で解けた問題)と
`qbase_*` はそれから作れる(回し直す必要はない)。**手順は `bench/adopt.sh <採用した label>`** にした
(直前の基準は `bench/res/prev_baseline/` に残す)。

```sh
bench/adopt.sh mychange     # baseline_*・tier1.txt・qbase_* を作り直す
```

## 長時間の実行(段2は30分〜2時間半かかる)

**必ず切り離して起動し、スクリプトは再開可能に書く。**
このマシンはバッテリ駆動で60分(AC接続で120分)の無操作スリープが効いており、
Windows のアイドル判定は**ユーザー入力の有無で決まる**ので、12コアを回していても
スリープする。スリープすると WSL2 の VM ごと落ち(`uptime` が `up 0 min` になる)、
走っていたものは失われる。

```sh
# セッションが終わっても生き残る形で起動する
nohup setsid bash myrun.sh > ~/benchtmp/myrun.log 2>&1 < /dev/null &
```

`quick.sh` と `compare.sh` は `BENCH_RESUME=1` を付けると**既に結果のある設定を
飛ばす**。中断したら同じコマンドを流し直せば、途中だった1設定だけをやり直す:

```sh
BENCH_RESUME=1 bench/compare.sh mychange
```

自前のスクリプトも同じ形にすること(出力ファイルを `[ -s "$out" ]` で見て飛ばす)。
なお**走っているプロセスが開いている出力ファイルを消してはいけない** ―
Linux では書き込み先が消えた inode に残り、結果が見えないまま失われる。

## 落とし穴

- **古いバイナリで測らない。** 必ず `build.sh` を通す。コミットの短縮ハッシュと md5 を出す。
- **問題リストを Windows 側で書かない。** CRLF になると最後の1問が `varignon
` という
  名前で渡り、証明器が異常終了しているのに「未解決」として静かに数えられる。
- 仕事量(`dfs_match` の回数)は機械の混み具合に依らないが、**壁時計の時間は依る**。
  時間を比べるときは他のベンチと同時に回さないこと。
- **ラベルを使い回さない。** `BENCH_RESUME=1` は、`res/` に同じラベルの結果があれば**回さずに再利用する**(意図した再開のための仕組み)。
  過去の実験と同じラベル(`spiral` など)で新しい実験を始めると、古い結果を新しい結果として読んでしまう ― 実際に一度やった
  (来歴 #68)。新しい実験には新しいラベルを使い、`ls res/ | sed -E 's/_q?(default|extras|skip|noise[0-9]+)\.tsv.*//' | sort -u` で既存のラベルを確かめる。
- **`qbench.sh` に渡す binary は絶対パス。** 問題ごとに別のディレクトリへ `cd` してから実行するので、相対パスだと全問が「見つからない(終了コード127)」になる。
- **壁時計の安全弁(`--time`、600秒)に当たる問題は決定的でない。** 仕事量の予算は決定的だが、重い問題は安全弁で止まることがあり、
  止まるかどうかは機械の混み具合で変わる(来歴 #74: 同じバイナリで centroid のノイズ5が 718万と 808万)。反転した問題の仕事量が予算より手前で止まっていたら、まずこれを疑う。
- **1プロセス 2.5GB のメモリ上限がある**(`bench.sh`・`qbench.sh` の `ulimit -v 2500000`)。上限を付ける前、図が暴走した実験で WSL ごと落ち、
  `/tmp` の作業ファイルが全部消えた(来歴 #75)。基準でも、ノイズ下で上限に当たって止まる未解決の問題がある(bench_2008armog10p6 のノイズ5・10 など)。
- **ノイズの設定は遅い。** 新しい定理や規則の課税は、図が大きくなるノイズ下で最も効く(#68: 平行四辺形の規則はノイズ10で仕事量 +253%)。
  1設定が10分を超えることがあるので、選抜の6設定を全部回す前に、default と noise5 だけで見当をつけてよい。

## 健全性の監査(偽のマージを数える)

```sh
bench/census.sh chk --no-merge-checks            # 全44問を監査付きで回す(マージ前の検査を外して、規則だけで健全かを見る)
bench/census.sh chk20 --no-merge-checks --noise=20
python3 bench/census_sum.py chk                  # 出どころ別の 真/偽/判定不能 と、問題ごとの最初の偽
```

`--audit-merges` は全てのマージと接続を実行の直前に数値で確かめる(探索は変えない)。問題ごとの最初の偽が、その問題の偽の連鎖の根。
前提を乱数座標で満たせない問題(thales など8問)の「偽」は誤警報の可能性があるので、集計から外して名前だけ出す。
2026-09-29 時点では、座標を置ける問題は既定とノイズ3水準で偽0件(来歴 #78・#79)。規則や定理を変えたら、採用の前にこれを回す。

## 保留問題とノイズの seed(汎化を測る)

調整に使った44問だけで採否を決めると、その44問に合わせた調整との区別が付かない(問題名で定理を入れる opt-in を禁じている理由と同じ)。

```sh
bench/heldout.sh mychange            # bench/heldout.txt(HAGeo-409 から機械的に読み込んだ、調整に使っていない問題)を default と noise5 で
bench/seeds.sh mychange              # ノイズの seed 2・3 で選抜(通常の quick.sh は seed 12345 の1つだけ)
```

保留問題は**採用の直前に測って報告するだけ**で、調整には使わない。解けなかった理由を調べて規則や語彙を足したら、その問題は保留ではなくなる
(`heldout.txt` から外して、`geom_solver hageo-list` で読める別の問題に置き換える)。詳しくは [設計ノート](../docs/notes/diagnostics.md) の「HAGeo-409 の取り込みと語彙の被覆率」。
