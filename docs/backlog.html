★ 失敗キャッシュの鍵に無関係な束縛まで入っている ― 同じ理由の失敗を、無関係な変数の値の数だけ作り直す
失敗した探索状態の鍵(state_signature)は束縛を全部入れて作っていた。ところが失敗の理由はたいてい束縛のうち数個しか使っていないので、無関係な変数 Z, W の値の組み合わせの数だけ、同じ失敗が別物として再発見され別々にキャッシュされる。図が大きいほど Z, W の取りうる値が増えるので、同じ失敗を作り直す回数がノイズの個数に対して掛け算で増える。SAT/SMT や制約充足でいう「nogood を explanation(核)付きで学習する」話にあたる。
入れた対処(--nogood-core): 鍵を「残っているパターンが実際に見る変数」だけに絞る。失敗する枝が見る束縛はそこに限られる(パターンの選び方も、破れの早期検査も、候補の展開も、残っているパターンの引数しか見ない)ので、核に入らない変数はその部分木の答えを変えられない。ただし枝の打ち切り(dfs_cap)は探索の順序に依存するので、「予算切れで失敗した」かどうかまでは一致しない ― 既存の失敗キャッシュと同じ近似。
計測(1問ずつ、--profile の「失敗キャッシュのエントリ数」): test_spiral_similarity 22,994→19,861(仕事量 27,462→27,059)、bench_2005ctstp1 313,146→284,708(742,344→736,854)、nine_point_full 626,966→642,825(807,600→780,026)、bench_2018chnwesternmop5 1,199,358→934,328(3,947,844→3,613,826、−8.5%)。ノイズ10では bench_2005ctstp1 427,960→294,105(−31%)、nine_point_full 647,620→540,937。
結論: 効く向きは一貫している(測った範囲で仕事量が増えた例は無い)が、予想した掛け算の潰れ方にはならなかった ― 仕事量で −1〜−8%。定理が小さく変数が密に絡んでいるので、残っているパターンの変数だけに絞っても核がほとんど束縛全体になってしまう。
選抜33問での結果(基準 → --nogood-core): 既定 32/32(仕事量 −1.5%)、extras 31→30(−15.1%)、skip 31→30(−9.4%)、ノイズ5 32→31(−4.2%)、ノイズ10 29→30(−5.5%)、ノイズ20 30→29(−5.3%)。仕事量は全設定で下がるが、解けた数は合計 −3。既定にはしない。
落ちる仕組み: 鍵が粗くなると、枝の刈られ方が変わって別の(長い)証明経路をたどることがある。bench_2012egmop1 は --central-angle だけなら解けるが 1,496,033 → 2,083,867 ステップかかるようになり、extras/skip/ノイズ5 の予算(--steps=1500000)を超えて落ちる。つまり「刈りすぎ」ではなく「予算の縁にいる問題が押し出される」。
試して外したこと: 鍵を核に絞るなら候補の並べ替えも核だけで決めるべき(核の外の束縛で順序が変わると、鍵が同じなのに予算の切れ方が変わる)と考えて DefinedBy の並べ替えの熱を核に限ったが、6設定すべてで1ステップも変わらなかった ― この定理たちでは核が結局ほぼ束縛全体になる。複雑さだけ増えるので戻した。
次の案: 「残っているパターンに現れる変数」は構文的な過大評価。深いところで失敗する枝は最初の1本で落ちることが多いので、実際に参照した変数を下から積み上げれば核はもっと小さくなる。ただしそれは鍵を引く前に分からない(ハッシュで引けず、包含判定が要る)ので、実装の形を変える必要がある。
--nogood-core で実装済み・既定にしない仕事量 −1.5〜−15%解けた数は合計 −3
★ 失敗キャッシュの無効化が大雑把すぎる ― 仕事量の2〜5割が「一度失敗と分かった枝を、無関係な変化のせいで捨てて歩き直す」ことに消えている
失敗キャッシュは各エントリに「この枝の結果はどの型に依存するか」(dep_mask)を持ち、その型の世代が変わると捨てる。世代は型ごとに1つの通し番号なので、その型の実体がどこかで1つでも変われば、その型に触れた全エントリが一斉に無効になる。
計測1(2026-09-23、--profile): dfs_match の呼び出しのうち、キャッシュに当たって即座に打ち切れた割合と、当たったのに世代が違って使えなかった割合:
bench_2022balkanmop1 ノイズ10 で 当たり 9.9% に対して無駄になった当たりが 51.3%(791,556 対 4,103,911)。ノイズ無しでも 7.2% 対 20.2%。bench_2005ctstp1 は 13.3% 対 38.7%。探索の半分近くが、すでに失敗と分かっている枝の歩き直し。
計測2(型世代を上げた理由の内訳): 4問とも同じ形で、接続関係の追加が 57〜59%、memoへの登録 18〜22%、実体の生成 12〜13%、マージ 8〜9%。接続関係の内訳では Point が約半分を占める。
計測3(依存マスクの幅): 失敗を記録するときのマスクは 1〜3ビットで98%、全ビットが立つことは無い。つまりマスクは既に細い。
試して外したこと(1) 型世代を「候補集合」と「接続関係」に分ける: 候補プールの列挙・memo検索は実体の生成/memo登録/マージで、is_connected と subobjects の列挙は接続関係/マージで無効化されるように、世代とマスクを8ビットに割った。接続関係が無効化の6割を占めるので効くと見込んだが、仕事量はほぼ動かなかった(bench_2005ctstp1 742,344→741,964、−0.05%)。計測3 の通りマスクは元々細く、問題は細さではなく、1本1本のビットが「その型のどこかで何かが起きた」という全体の通し番号であること。link(Point) だけでも数千回上がるので、1ビットしか立っていないエントリでも普通に死ぬ。複雑さと記憶量([u64;4]→[u64;8])に見合わないので戻した。
試して外したこと(2) 変化の無い定理の全探索タスクを積まない: 「前回その定理を最後まで走査したときから、その定理が読む型の世代も cap も変わっていなければ積まない」を入れたが、省けたタスクは全設定で0件。sweep と sweep のあいだに何百ものタスクが実行され結論が適用されるので、4つの型世代は必ず全部動いている。粒度が sweep 単位では粗すぎる。
次にやるべきこと: 残る軸は「どの型か」ではなく「どの実体か」。その枝が実際に読んだ代表元を覚えて、それらが変わったときだけ捨てる。型ごとの通し番号を実体ごとの版番号に落とす形になり、索引を持つ関係マッチング(b30)と同じ構造を要求する ― b30 を先にやるべき根拠がここで1つ増えた。
関連: シード経路(差分起動)は過去6回試して6回とも撤回されている(#7)。ただし6回とも全体sweepに「足す」形で、減らす側は上の(2)が初めてで、それも空振りだった。

★ 入れ子ループ結合をやめて、関係マッチング+最悪計算量最適結合にする(第一歩の semi-join は既定で投入済み)
dfs_match は毎ステップ estimate_cost で一番安いパターンを選ぶ貪欲な入れ子ループ結合で、中間結果が爆発するから heat_cap / fanout_heat_cap で打ち切っている ― つまり候補capは入れ子ループ結合の爆発に対する対症療法で、b27 の「広げる時機」もその調整でしかない。
対応するのが e-graph 側の既製技術で、演算子ごとに関係(列は同値類の id)を張り、マッチングを連言クエリとして Generic Join / Leapfrog Triejoin で評価する(relational e-matching、POPL 2022 / egglog)。効く理由が3つある: (1) 中間結果ではなく実際の出力サイズ(AGM 上界)で抑えられるので、capで切り捨てる必要が構造的に減る。(2) 変数順序に依存しない保証があるので、方針Bの「定理の順序で±15%動く」問題に別角度から答えが出る。(3) ノイズは関係にタプルを足すだけなので、劣化が掛け算でなく出力サイズなりになる。
第一歩(投入済み、§04 #55): 候補を cap で切る前に、まだ残っているパターンのうち相手が束縛済みのもの(Connected / Identical / Distinct)で絞る semi-join reduction。解は1つも減らず、全44問×6設定で仕事量 −23.4〜−33.3%。既定にした(--no-semijoin で戻せる)。
まだやっていない本体: 「パターンを選んで候補を出す」のをやめ、変数を選んで、その変数に触れる全パターンの候補集合を交差させる形にする。semi-join は1本のパターンから出した候補を他で絞るだけなので、最初に選んだパターンの候補数がそのまま上限になる(例: Connected(P,L1) ∧ Connected(P,L2) は L1 の subobjects を全部出してから L2 で絞る)。交差にすれば小さい方から当たれるうえ、出力サイズで抑えられるので cap 自体が要らなくなる可能性がある。
要る部品: (1) 関係ごとの索引(いまは components[].subobjects の線形走査と connected_pairs_for_types の型ペアキャッシュしかない)、(2) 変数順序の決め方、(3) b29 で必要と分かった実体単位の依存追跡 ― 索引を持つとこれも自然に載る。
手を付ける順序は測って決まった(§04 #56): (2) の変数順序だけ先に入れると悪化する。「いちばん縛られている変数から束縛する」は完全な探索なら正しいが、cap があると「どの候補が切り捨てられるか」まで変わるため、解ける問題が入れ替わりテストも落ちた(bench_2022balkanmop1 ノイズ10 は 0→1 になる一方 bench_2018chnwesternmop5 が 1→0、bench_2005ctstp1 ノイズ10 は9倍に)。先に交差で cap 自体を不要にすること。変数順序はその後でないと良し悪しが測れない。

関連度フィルタ(SInE / MePo)― 「巨大な前提のうちほとんどが無関係」はノイズ問題と同じ形
Sledgehammer の MePo と Vampire の SInE は「巨大な公理集合のうちほとんどがゴールと無関係」という、方針E のノイズ問題とまったく同じ状況のために作られたもの。ゴールに現れる記号から出発し、記号の希少性で重み付けしながら反復的に関連する事実を引き込む。
いまの heat はその手作り版に見えるが、MePo は「ゴールからの距離」と「記号の希少性」を明示的に分け、行き詰まったら半径を広げる段階構成を持っている。heat の初期値をこの方式で与えるのは今の構造に載せやすい。
注意: これは問題ごとに定理を手で選ぶ opt-in とは別物(ゴールから自動で導出し、行き詰まりに応じて広げる)。ただし「候補を落とす」機構である点は共通なので、広げ方を先に決めてから入れること。

マージの由来を出す ― 証明付き合同閉包(proof forest / egg の explanation)
マージ監査(§04)は数値で真偽を見るところまでで、なぜそのマージが起きたかは出せない。union-find に証明の辺を張る proof forest(Nieuwenhuis–Oliveras)や egg の explanation が既製の答えで、偽マージの由来を機械的に辿れるようになる。定理の書き方の誤りを見つける手間が大きく減る。
取らないもの: LCF 風カーネル、依存型、tactic 言語、完全な superposition。こちらの主張は地の等式・接続関係なので、その表現力は要らない。

★ 候補capを広げるのが遅すぎる ― 需要作図が尽きるまで待つので、その間に図が膨らむ
行き詰まったときの手は「補助線・交点 → 有向角 → 第2交点 → 中点 → 目標からの逆算 → 候補capの拡大」の順で、候補capの拡大は需要作図が全部尽きてからになる。ところが図が大きいほど需要作図は尽きにくく、cap を広げる番が来る頃には図が膨らみ切っている。
実例(test_spiral_similarity + ノイズ5): 既定では有向角の需要が78回走り、cap は3回広がったものの手遅れで、2,813,981ステップ使って解けない。最初から --fanout-heat-cap=40 にすると 11,014ステップで解ける。--skip-recovery=angle,second,mid(図を広げる手を外す)でも19,891ステップで解ける。
試した対処: --widen-first(需要作図より先に広げる)はノイズ下で +5問(ノイズ5で30→32、10で28→29、20で28→30)だが、きれいな既定設定では仕事量 +72%。「cap が実際に候補を切り捨てたときだけ先に広げる」条件を足しても、自己束縛の切り捨てはきれいな図でも普通に起きるので同じ結果。--widen-every=N(行き詰まりN回ごとに先に広げる)の N=2 は、きれいな図で +35%、ノイズ5の対象問題は解ける。
次の案: 広げる対象を全体ではなく「切り捨てが実際に起きた型・定理」に絞る。あるいは需要作図の側に上限を設け、同じ種類の需要を何度も繰り返さない。
ノイズ5で2問・ノイズ10で4問が落ちる主因きれいな図での増加を抑えるのが課題
★ 仕事量に数えられない数値チェックが、実体が増えると時間の大半を占める ― 仕事量予算が時間を抑えられない
作図画面の証明を秒から仕事量(dfs_match の回数)の予算に移したところ、自由作図で実体が数百個になった円の図で、1回の run_step が仕事量17万で46秒かかった(solve の典型は毎秒15万〜25万、ここは毎秒約3,700)。スタックを採ると、時間はほぼ全て propagate_conic_uniqueness が呼ぶ numeric_plausibility_check に消えていた。内訳は (1) 前提の曲線の洗い出しと祖先の自由点集めを毎回図全体から辿り直すこと、(2) 検算そのもの(大きな祖先の評価)を二次曲線の組の数だけ繰り返すこと。(1) は構造の世代で無効化するキャッシュにして 46秒→6秒(結果は不変、§04 #49)。(2) は残っていて、二次曲線の組が増えるほど効く。
方針Eとの関係: 無関係な作図を足すと円・二次曲線が増え、仕事量は同じでも時間が大きく伸びる ― ノイズへの頑健性を測ると最初に当たる壁。候補: 検算の結果を(代表元の組, 構造の世代)で覚える、評価の中間値を同じ座標のまま使い回す、数値チェックのコストを仕事量に数える(solve の結果が変わるので要計測)。
1回の run_step が46秒(キャッシュ後6秒)ノイズを足した図で最初に効く
「その点なしで曲線を評価できるか」の判定が、辿る順序で変わる
evaluation_requires_point は循環に当たった節点そのものはメモしないが、その結果(「不可欠」と倒した値)を使った親の結果はメモする。同じ memo で別の曲線から辿り直すと答えが変わる。数値評価器を1つにまとめたとき(§04)に表に出た: p進の評価器は点ごとに memo を使い回し、有限体の評価器は曲線ごとに作り直していたので、同じ図で2つの評価器の判定が食い違っていた。使い回す方に揃えると --skip-recovery=angle,target で bench_2018chnwesternmop5 の二次曲線の結合の判定が変わり、解けない→解けるになった(証明は extract_proof で厳密)。今は作り直す方に揃えて挙動を変えていない。循環の影響を受けた結果を親にも伝えてメモしないようにすれば順序によらない判定になるが、循環の多い図でメモが効かず遅くなる恐れがあるので、速度と結果の両方を測ってから入れる。

★ 探索が定理を試す順序に大きく左右される ― 解けるかどうかが順序の運に依存している
§04「同じ優先度のタスクを定理の登録順に取り出し…」の実測で、定理の登録順を変えるだけで両方で解けた問題の仕事量が ±15% 程度振れ、個別には bench_2012egmop1 +358%・nine_point_full +115% のように大きく動き、bench_2018chnwesternmop5 は7通り中3通りで解けなくなった。筋の通った並べ方(逆順・パターン数順・射影先頭)はどれも登録順に勝たず、登録順を詰めても問題が変われば効かない見込み。順序に鈍感な探索にする方が本筋 ― 例えば1回の run_step の途中でマージが起きても、同じ全探索の残りのタスクには古い図の上での結果を使わせない(全タスクを試してから結論を適用する)と、順序の影響がどれだけ減るかを測る。
