00

今、並行して走っている4つの方針

ユーザー指示「マッチングの高速化と射影幾何への移行のタスクをきちんと分けないと両方中途半端になってしまいそう」を受けて新設した節。それぞれ独立にscopeし、混ぜて着手しないための一覧。詳細な来歴は§04、個別の未着手項目は§05を参照。

方針A特殊ケースを型タグでなくincidenceで表現する統一主要3種は完了
方針A 射影幾何
原則(メモリ済み): 「本質的には普通のオブジェクトの特殊ケース」は専用EntityTypeを作らず、標準の型+基準点へのincidenceで表す。Direction→Point(line_infinityとの接続)、Circle→Conic(円周点I,Jとの接続)、Angle→Scalar(AnglePairは元々複比として実装済みだった)の3種を撤廃済み。次点はユーザー明示の優先順位: 方冪 → 直角三角形 → 二等辺三角形関連定理の射影形移植(トロメイの定理は汎用性が低いため明示的に後回し)。未着手。
方針B型統合が暗黙にキャッシュ粒度も粗くする問題への対処82/96まで到達
方針B マッチング高速化
方針Aの副作用として、型統合のたびに共有キャッシュ(type_generation系)の無効化粒度が粗くなり性能回帰を起こすことが判明(Angle統合で69/96→57/96)。angle_generation/plain_scalar_generationという独立カウンタへの分離で解消し、73/96→76/96まで回復・改善。射影定理5種を全問題共通のデフォルトから外しopt-in化したのも実質この路線の成果。ユーザー提案「接続の弱いfailed pathは型に関わらず保持できるはず」を受け、MatchTask::cached_failed_pathsの無効化を「定理単位で1つでも型が変われば全滅」から「個々の失敗状態ごとの依存マスク(entity_type_bit)」に細分化し、さらにタスクをまたいだ永続グローバルキャッシュへ昇格させて76/96→78/96(3回とも完全に同一の結果、従来揺れていたnine_point_full/orthocenterが一度も落ちなくなった)に到達。続けてユーザー提案「熱cap関連のパラメータを調整できないか、行き詰まったら幅を広げる」に基づき、狭い(=速い)fanout_heat_capから始め手詰まり時だけ段階的に広げる適応的な探索を実装し、82/96まで更新した(§04参照)。今後の教訓: 型を統合するたびに「候補プールの汚染」だけでなく「キャッシュ無効化粒度の粗大化」も点検すること(メモリ済み)。単一の固定パラメータで複数の問題を同時に最適化しようとすると綱引きが起きる場合、適応的な段階拡張が有効な解決策になりうる。
方針C個別定理の追加より、汎用の補助構成ヒューリスティックを優先実験継続中
方針C MCTS/補助構成
ユーザー指示「無闇に定理を追加してもノイズが増えるだけ、ondemand作図やmctsの補助点作図を改善すべき」に基づく路線。SecondIntersectionOfLineAndConic(直線と二次曲線のもう一方の交点)を汎用プリミティブとして追加したが、A/B検証の結果これ自体が決め手だった例はまだ無い。より大きな発見: 既定実行は--mctsを無効にしており、需要駆動の補助構成が尽きると探索を完全に打ち切る(main.rsのリカバリーフェーズ)。bench_2018silkroadp1/bench_2005ctstp1は--mcts --time=30なら解けることを確認済み――既定の5秒予算では時間が足りないだけで、定理不足ではない。MCTSを既定で有効化する実験は既定5秒予算のままだと75/96とほぼ横ばい(nine_point_full/orthocenterの安定性とのトレードオフ)で、時間予算を上げる/MCTSの健全性チェックを強化するところまで踏み込まないと純増にならない。
2026-09-16 の実測(§04 --origins): 需要駆動の補助線を外すと31→15問、交点を外すと31→29問 ― 解けている問題の約半分はこの路線の手で支えられている。一方で目標から逆算する作図は一度も効いておらず、MCTSは既定で無効なので、「何を作図するか」を目標側から決める手はまだ実質無い(§05)。
方針D個別問題向けの専用定理は最小限に具体案は§05に温存
方針D 定理追加
ユーザー方針: 定理を無闇に増やすとノイズ(UCB1バンディットの試行対象が増え、無関係な問題まで「一度は試す」コストを払う§05-#10)が増えるだけなので、本当に汎用性のある定理・作図プリミティブでなければ追加しない。ただし旧atlas診断(§05-#11, #12)で「新定理が必要」と特定済みの具体的なギャップ(bench_2011balkanmop1が要求する2直線版スパイラル相似、bench_2012egmop1/2018chnwesternmop5/2005usamop3固有の中間補題)は、方針Cで届かなければ最終手段として温存する。
01

ファイル構成と入口

1つのRustバイナリ(geom_solver)に、証明・発見・退化解析・ベンチ掃引・Web配信の入口が同居している。src/mmp_core/が図形の表現(e-graph)、src/logic_core/がその上を探索する証明器、という二層が骨格。

src/main.rs

入口。未知のフラグの検出とサブコマンドの振り分け、extract-proof。

src/solve.rs

問題を1つ解くメインループ。オプションの解析(SolveOptions)→ 問題の読み込み → run_step → 目標判定(GoalChecker)→ 行き詰まったら回復(Recovery: 需要駆動の作図 → 候補capの拡大 → MCTS)、の一巡と、終了時のレポート。

src/cli.rs

オプションの一覧表とhelp/list。知らないフラグは黙って無視せずエラーにする(「変えたつもりで既定値のまま走る」事故を止めるため)。

src/mmp_core/mod.rs

EGraph・GeoEntity・Definition・EntityType・Fact・Justification。生の構造を書き換える4ゲートウェイもここ(§03)。

mmp_core/congruence.rs

apply_congruence_closureと、直線・二次曲線・交点の一意性の局所伝播。マージの実行(merge_entities_justified)もここ。

mmp_core/eval.rs

有限体上の数値評価。numeric_plausibility_check(マージ前の裏付け)とcached_degree(動点法の代数的次数)。

mmp_core/proof.rs

explain_identical: なぜ2つが同じ同値類に入ったかを「証明の森」から復元する。人間向けのgenerate_proofも。

mmp_core/raw_proof.rs

全マージ履歴のダンプと、その再帰的な検証(verify_identical)。extract-proofサブコマンドの実体で、合流履歴を前向き・逆向きの両方に辿る。

mmp_core/query.rs

図の状態を問い合わせる述語。merged_free_points(図の崩壊検出)はここ。

src/logic_core/theorem.rs

定理の書き方そのもの: Pattern・TheoremDef・MatchTask・TheoremBanditStats。データ構造と純粋関数だけで、探索の状態は持たない。

logic_core/prover.rs

ProverEngineの状態(e-graph・既知の事実・バンディット統計・失敗パスの永続キャッシュ)と、マッチ成立後の作図・結論の適用。

logic_core/cost.rs

「次にどのパターンを見ると安いか」(estimate_cost)と「候補が多いときどこまで絞るか」(熱capまわり)。見積もりと枝刈りの方針だけをここに集めてある。

logic_core/matcher.rs

深さ優先探索の本体(dfs_match)と、fact_typeごとの候補の展開。どれを選ぶかの方針はcost.rsに分離済み。

logic_core/blackboard.rs

探索の司令塔。タスク待ち行列を回し、行き詰まったときの需要駆動の補助作図(resolve_*_demands)で図を伸ばす。

src/theorems.rs

定理の定義(23件)。get_all_theorems17件 + get_projective_theorems5件(既定で有効) + 中心角の定理1件(opt-in)。

src/problems/

ベンチ44問。単体検証(test_*)・古典幾何・HAGeo-409由来(bench_*)。mod.rsに「目標が数値的にも本当に成り立つか」の検査を置いてある。

src/trace.rs

診断(--trace)。使った仕事のうちどれが証明に残ったかを、発火の記録と証明の遡りを突き合わせて測る(§05)。

action_space.rs / mcts.rs

補助構成の行動空間と、それを探索するMCTS。需要駆動の回復も尽きたときの最後の手段(既定は無効)。

padic.rs / padic_eval.rs

図形を退化させたときの振る舞いの解析。どの実体どうしが「一緒に潰れる」かを観測し、熱のボーナス伝播に使う(--degen-heat)。

discover*.rs

目標を持たない自由作図モード。作図を伸ばしながら非自明な一致を探し、見つけたものを証明しにいく。

serve.rs + web/

ブラウザUI。発見結果を1件ずつ流し、面白さ順に並べ替えて証明の成否まで見せる。

sweep.rs

全問題×パラメータ組み合わせの掃引。仕事量予算なので結果は機械の混み具合に左右されない。

mmp_math / mmp_calculators / mmp_tester

法998244353の有限体演算、各Definitionの具体的な計算、最終的な数値サニティチェック。

入口(サブコマンド)は次の通り。いずれも geom_solver help に一覧が出る。

geom_solver <問題名>

証明を試す。--steps(既定800万)が本当の予算で、--time(既定600秒)は暴走時の安全弁。診断は--stats/--profile/--trace/--origins(作図の出どころ別の効き)。行き詰まり時の手を個別に外すA/Bは--skip-recovery=line,point,second,mid,angle,target。長さを橋渡しする定理は--length-theorems。

geom_solver sweep

全37問を順に解いて成否と所要時間を集計する。--varyでパラメータを振れる。

geom_solver diagnose

問題ファイルに書いた人間の証明の筋書き(SKETCH)に沿って、補助作図と手順1..kを順に前提として与え、各手順が自力で出るかを表にする。解けない問題がどの手順で詰まるかを名指しする。

geom_solver discover

目標なしの自由作図から非自明な性質を探す。--proveで見つけた性質の証明まで試す。

geom_solver discover-degenerate

図を退化させて「一緒に潰れる」実体の組を観測する。

geom_solver extract-proof

記録したマージ履歴から、目標までの証明を再帰的に展開して監査する。

geom_solver serve

ブラウザUIを配信する。発見結果を逐次ストリームする。

02

パイプライン全体

1問につき EGraph::new() → 問題ファイルによる初期条件の投入 → BlackboardEngine によるタスクキュー駆動の定理マッチング、という流れ。探索が完全に手詰まる(Stall)たびにオンデマンド作図の回復フェーズへ落ち、それも尽きれば熱capの段階拡張、最後にMCTSへ委ねる。予算は壁時計の秒ではなくdfs_matchの呼び出し回数(--steps、既定800万)で測るので、同じコード・同じ問題なら何度流しても同じ結果になる。

03

マッチングの中身(dfs_match)

MatchTask は1つの定理・1つの束縛状態を表し、優先度付きキューで管理される。TheoremDef.patterns を先頭から満たしていくバックトラック探索で、パターンの型(Identical / Connected / DefinedBy / 汎用)ごとに専用の列挙ロジックを持つ。

Identical(v1, v2)

両方未束縛なら型で絞った代表元へ自己束縛(RETE的に定理をまたいで共有キャッシュ済み)。

Connected(child, parent)

e-graphの subobjects を辿る接続判定。両方未束縛のジョインも型だけで決まるため共有キャッシュ済み。

DefinedBy(…, result)

親が揃っていれば memo の O(1) ルックアップ、無ければその場で構成する — マッチングが副作用を持つという設計上の緊張点。

failed_paths

「この束縛状態はもう行き止まり」の記憶。定理ごとの永続マップで、タスクをまたいで共有される。無効化は型別の依存マスクで個別に判定する。

パターンのビットマスク

「まだ消費していないパターン」はu64のビットで持つ。定理のパターン列は不変なので実体は借りるだけで、分岐のたびのヒープ確保が要らない。

順序/相異の前倒し

Order/Distinctは全変数が揃うまでestimate_costが無限大を返すので最後まで選ばれない。束縛済みの範囲だけで毎回検査し、最も早い時点で枝を切る。

UCB1バンディット

シードなし全探索タスクの優先度を、定理ごとの過去の成功率+探索ボーナスで決める。未試行の定理は常に一度は試す。

4つのゲートウェイ

create_entity / merge_entities / link_logical_incidence / insert_memo。e-graphの生の構造を書き換える経路をここに集約し、type_generation の更新漏れを構造的に防いでいる。
