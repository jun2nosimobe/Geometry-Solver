今、並行して走っている5つの方針

性質の違う作業を混ぜて着手しないための一覧(2026-09-30 時点)。数字は既定設定・44問・仕事量予算8,000,000での値。変更ごとの詳細は§04、未着手の項目は§05。

方針A射影幾何と、規則の側で保つ健全性座標を置ける問題では検査なしで偽0
原則: 「普通の図形の特殊ケース」には専用の EntityType を作らず、標準の型と基準の実体への接続で表す(方向 = 無限遠直線上の点、円 = 虚円点 I, J を通る二次曲線、有向角 = 無限遠直線上の複比)。健全性は規則の側で保つ: 定理に非退化条件を書き(#78)、数値の検算を探索前に一度だけ置く固定座標にした(#79)。座標を置ける問題では、マージ前の検査を外して監査しても偽のマージが0件(検査は安全網として残す)。代数的な追跡(AR)の等式も、定義の写像を数値で確かめ、図の上で同じ点の組を使わない(#85)。
監査は時刻つき(各ステップの前提がそれより前に成り立っていたか・説明が循環していないか)で、解けている39問全てがギャップなし(#87・#88)。残る穴: 座標を置けない2問(8問中6問は検算専用の代数的な置き方で置けた、#87)では数値の検算も AR も効かない(b46)。目標が共円・接続の8問も、目標到達時の検算と深い証明の監査を通す(#86)。証明の各ステップの数値検算は未実施(b44)。
方針B探索の効率と再現性39/44・決定的
予算は壁時計ではなく仕事量(dfs_match の呼び出し回数。AR の行演算は16回で1)で測り、乱数もシード固定なので、同じ設定なら結果が1ステップも変わらない。
マージの連鎖: e-graph の合同閉包は worklist でマージを連鎖させるが、定理の層は1回の全探索(sweep)ごとにしか連鎖しない(差分だけ試し直す seeded rematch は既定で無効)。AR は手詰まりのたびに、角・複比・比・相似の線形な関係を格子で一度に閉じる ― 格子は毎回作り直す(差分で積むと古い記号の行と証明の前提が膨らんだ。#85)。
現状の課題: 定理を試す順序に左右される(登録順で仕事量±15%)。dfs_match は貪欲な入れ子ループ結合(b30)。
方針C個別の定理より、汎用の補助作図需要駆動 + 最後の手
行き詰まったときの手は需要駆動の作図(補助線 → 交点 → 有向角 → もう一方の交点 → 中点 → 目標からの逆算)で、尽きたら候補capを広げ、最後に問題に依らない補助作図(熱い点どうしの中点・熱い直線どうしの交点、#72)と数値で選ぶ補助作図(候補を固定座標で試作し、新しい一致を生むものを作る、#80)を同じ回に試す。MCTS は既定で無効。
次の案(ユーザー): ある程度探索したら、使われなかった補助作図を捨てて作り直す。圧縮した証明に出ない補助作図は 15〜55%(b48)。
方針D定理を増やさず、AR の等式に置き換える方冪・交わる弦の相似を置き換えた
定理を増やすと無関係な問題にも試行の仕事量が乗り、問題名で定理を入れる opt-in は使わない。代わりに、定理が言っていることを形式的な対数の線形な等式として AR に入れる: 有向角・点と線束の複比(#82)、円・透視射影・シュタイナー(#83)、比と平行(#84)、メネラウスとチェバ(#88)、等方線束での長さの比と相似・相似で対応する点(#85)。AR が有効なら「共点二弦の相似」と「交わる弦の相似」を既定で外し、幾何平均 −11.9%・+3問。
まだ外せない: 円・射影の定理と角の足し算の規則(座標を置けない問題では AR が働かない、定理が角・複比の実体を作る働きを置き換えられない)。長さは足し算を扱わず比のまま入れる方針(ユーザー)。
方針E無駄な作図のノイズを足しても解ける頑健性ノイズ5で34・10で34・20で33
ユーザー方針(2026-09-17): 問題の初期作図に証明と無関係な作図を足しても解ける頑健性を目指す。改善は「余計な実体があっても探索のコストと結果が変わらない」方向を優先し、特定の問題の作図の並びに合わせた調整は採らない。--noise=N で測る(#50)。
今の弱さ: ノイズを足すと全探索の回数が増える(b29)。AR の併合で手詰まりの時期がずれると道筋が変わり、bench_2012egmop1 はノイズ5で12倍重い(ノイズ20では逆に軽い)。
01

ファイル構成と入口

1つのRustバイナリ(geom_solver)に、証明・発見・退化解析・ベンチ掃引・Web配信の入口が同居している。src/mmp_core/が図形の表現(e-graph)、src/logic_core/がその上を探索する証明器、という二層が骨格。

src/main.rs

入口。未知のフラグの検出とサブコマンドの振り分け、extract-proof。

src/solve.rs

問題を1つ解くメインループ。オプションの解析(SolveOptions)→ 問題の読み込み(ノイズ・筋書き)→ 定理集合 → 前提の投入 → 探索の前の準備(prepare)→ run_step → 目標判定(GoalChecker)→ 行き詰まったら手詰まりの一手(on_stall: AR と回復を同じ回に。尽きたら --mcts のときだけ MCTS)、の一巡と、終了時のレポート。diagnose(--sketch)と sweep もここを通る。

src/cli.rs

オプションの一覧表とhelp/list。知らないフラグは黙って無視せずエラーにする(「変えたつもりで既定値のまま走る」事故を止めるため)。

src/mmp_core/mod.rs

EGraph・GeoEntity・Definition・EntityType・Fact・Justification。生の構造を書き換える4ゲートウェイもここ(§03)。

mmp_core/congruence.rs

apply_congruence_closureと、直線・二次曲線・交点の一意性の局所伝播。マージの実行(merge_entities_justified)もここ。

mmp_core/fixed_coords.rs

固定座標: 前提が乱数座標で成り立つなら探索の前に一度だけ座標を置き、各実体を元の定義から計算する(マージに依存しない)。マージ前の検査・結論の検算・非退化条件・AR の写像の確認・数値で選ぶ補助作図が使う(#79)。

mmp_core/algebraic.rs

検算専用の代数的な置き方。乱数の座標では前提が成り立たない図(直線と円の両方に乗る点・「OP = OA」のような前提)で、前提を媒介変数の有理関数として標本から復元し、有限体の上で根を求めて自由点を置く。次数の評価には使わない(#87)。

mmp_core/eval.rs

有限体上の数値評価。numeric_plausibility_check(マージ前と目標到達時の裏付け)とcached_degree(動点法の代数的次数)。

mmp_core/coords.rs

数の表現によらない評価の骨組み: 同値類の評価(同居する定義を順に試す・循環の検出)と、自由点の置き方(前提の曲線の上に置く・循環の解消・最後の検証)。有限体(eval.rs)・p進(padic_eval.rs)・実数(discover_viz.rs)の3つが共有する。

mmp_core/proof.rs

explain_identical: なぜ2つが同じ同値類に入ったかを「証明の森」から復元する。人間向けのgenerate_proofも。

mmp_core/raw_proof.rs

全マージ履歴のダンプと、その再帰的な検証(verify_identical)。extract-proofサブコマンドの実体で、合流履歴を前向き・逆向きの両方に辿る。

mmp_core/query.rs

図の状態を問い合わせる述語。merged_free_points(図の崩壊検出)はここ。

src/logic_core/theorem.rs

定理の書き方そのもの: Pattern・TheoremDef・MatchTask・TheoremBanditStats。データ構造と純粋関数だけで、探索の状態は持たない。

logic_core/prover.rs

ProverEngineの状態(e-graph・既知の事実・バンディット統計・失敗パスの永続キャッシュ)と、マッチ成立後の作図・結論の適用。

logic_core/cost.rs

「次にどのパターンを見ると安いか」(estimate_cost)と「候補が多いときどこまで絞るか」(熱capまわり)。見積もりと枝刈りの方針だけをここに集めてある。

logic_core/matcher.rs

深さ優先探索の本体(dfs_match)と、fact_typeごとの候補の展開。どれを選ぶかの方針はcost.rsに分離済み。

logic_core/blackboard.rs

探索の司令塔。タスク待ち行列を回し、行き詰まったときはrecover(需要駆動の補助作図 → 候補capの拡大 → 汎用・数値で選ぶ補助作図)で図を伸ばす。探索の前の準備(prepare: 前提の凍結 → 固定座標 → 検査の設定)と手詰まりの一手(on_stall: AR と recover を同じ回に)は solve・serve・discover で共通(#86)。

logic_core/ar.rs

代数的な追跡(AR)。2点の差の形式的な対数を記号にし、有向角・複比・比・長さ(等方線束)・相似の等式を整数の格子(ℤⁿ ⊕ ℤ/4、エルミート標準形)で閉じて、同値類・方向・円への接続を併合する。手詰まりのたびに格子を作り直す(#82〜#85)。規則の一覧(状況 → 格子に足す関係式、格子で言えたら → 結論)は §07。

logic_core/numeric_aux.rs

数値で選ぶ補助作図。交点・中点・垂線や平行線との交点・第2交点の候補を固定座標で試作し、既存の直線・円に乗る/点と重なる/新しく共円・共線になるものを点数順に作る(#80)。

src/theorems.rs

定理の定義(27件)。theorem_set の既定は24件(基本16・長さ1・中心角1・射影5・交わる弦の相似1)、--rules で弦・平行四辺形・同じ向きのスパイラル相似。solve は AR が有効なら方冪と交わる弦の相似の2件を外して22件で探索する(--chord-theorems で残す)。

theorem_lint.rs / theorem_atlas.rs

定理の書き方の検査(役割・規模・対称性・証人)と、§07 定理の頁の元データ(geom_solver theorem-atlas)。

noise.rs / sketch.rs

証明と無関係な作図を足すノイズ(--noise、方針E)と、人間の証明の筋書き(SKETCH)を段階的に前提として与える diagnose。

src/problems/

ベンチ44問。単体検証(test_*)・古典幾何・HAGeo-409由来(bench_*)。mod.rsに「目標が数値的にも本当に成り立つか」の検査を置いてある。

src/trace.rs

診断(--trace)。使った仕事のうちどれが証明に残ったかを、発火の記録と証明の遡りを突き合わせて測る(§05)。

action_space.rs / mcts.rs

補助構成の行動空間と、それを探索するMCTS。需要駆動の回復も尽きたときの最後の手段(既定は無効)。

padic.rs / padic_eval.rs

図形を退化させたときの振る舞いの解析。どの実体どうしが「一緒に潰れる」かを観測し、熱のボーナス伝播に使う(--degen-heat)。

discover*.rs

目標を持たない自由作図モード。作図を伸ばしながら非自明な一致を探し、見つけたものを証明しにいく。

serve.rs + web/

ブラウザUI。発見結果を1件ずつ流し、面白さ順に並べ替えて証明の成否まで見せる。

sweep.rs

全問題×パラメータ組み合わせの掃引。仕事量予算なので結果は機械の混み具合に左右されない。

mmp_math / mmp_calculators

法998244353の有限体演算と、各Definitionの具体的な計算。

入口(サブコマンド)は次の通り。いずれも geom_solver help に一覧が出る。

geom_solver <問題名>

証明を試す。--steps(既定800万)が本当の予算で、--time(既定600秒)は暴走時の安全弁。診断は--stats/--profile/--trace/--origins。--audit-merges は全てのマージ・接続を固定座標で確かめて出どころ別に真・偽・判定不能を数え、--no-merge-checks と組むと規則だけで健全かを測れる(bench/census.sh)。A/B 用に --no-ar・--chord-theorems・--drop-theorems=名前,…・--no-numeric-aux・--no-fixed-coords・--no-nondegeneracy・--skip-recovery=…。一覧は geom_solver help。

geom_solver sweep

全44問を順に解いて成否と所要時間を集計する。--varyでパラメータを振れる。

geom_solver diagnose

問題ファイルに書いた人間の証明の筋書き(SKETCH)に沿って、補助作図と手順1..kを順に前提として与え、各手順が自力で出るかを表にする。解けない問題がどの手順で詰まるかを名指しする。

geom_solver discover

目標なしの自由作図から非自明な性質を探す。--proveで見つけた性質の証明まで試す。

geom_solver discover-degenerate

図を退化させて「一緒に潰れる」実体の組を観測する。

geom_solver extract-proof

記録したマージ履歴から、目標までの証明を再帰的に展開して監査する。

geom_solver serve

ブラウザUIを配信する。発見結果を逐次ストリームし、1件ずつ証明を試す(予算は solve と同じ仕事量)。

02

パイプライン全体

solve の1問の流れ。前提を入れた後、前提が乱数座標で成り立つなら固定座標を置き、以後の検算・非退化条件・AR・数値で選ぶ補助作図はすべてこの座標の上で行う。探索はタスク待ち行列の定理マッチングで進み、完全に手詰まる(Stall)たびに、同じ回に AR と回復を行う。予算は仕事量(--steps、既定800万)なので、同じコード・同じ問題なら何度流しても同じ結果になる。

入口ごとの違い

探索の前の準備(BlackboardEngine::prepare)、手詰まりの一手(on_stall)、定理集合(theorem_set)、目標の判定(goal_status)は3つの入口で共通(#86)。違いは次の3点だけ。

solve(diagnose・sweep も)

オプションで各部品を外せる(A/B 用)。回復は RecoveryOptions::standard()(中点の需要なし)。目標に届いたら extract-proof の深い監査(一致の目標は合流経路、接続・共円の目標は目標の接続の由来から)。MCTS は --mcts のときだけ。

serve の証明試行

発見した主張をまとめて1つの図で証明する(prove_together)。回復は standard に中点の需要を足す(自由作図の主張では中点1つが足りないだけの形が多い)。壁時計の上限15秒。深い監査は無く、goal_status(崩壊・数値の検算)まで。

discover の証明試行・仮説プロービング

build_full_engine で serve と同じ組み立て。プロービングは予想を仮定として併合して何が導かれるかを見る。

連携の穴(2026-09-30 の点検)

1. serve・discover が solve の探索を使っていなかった → 直した

固定座標・結論の検算・AR・数値で選ぶ補助作図が solve.rs の中だけにあった。prepare・on_stall・RecoveryOptions::standard() に1本化し、作図画面の4つの図で証明できた件数が 55 → 67 件。solve は37問×6設定で1ステップも変わらない(#86)。

2. 定理集合の2件の除外が theorem_set の外にあった → 直した

TheoremSetOptions::ar_replaces_chord に移し、§07 と定理の検査も同じ判定になった(2件は「--chord-theorems(AR が置き換え)」と表示)。

3. 共円・接続の目標(8問)が監査されなかった → 直した

固定座標で目標の接続を確かめ(前提が乱数座標で成り立たない図では誤警報になるので固定座標でだけ)、RawProof::verify_incidences で目標の接続の記録(記録が無ければ、点・曲線の同値類で定義から従う組)と、そこまでの合流経路を監査する。7問で監査が回り、ギャップ0。

4. MCTS の数値ショートカット判定は Identical だけ(残り)

MCTS が構成に関わった実行で、数値検証だけが根拠の局所ショートカットを含む到達を却下する判定。MCTS は既定で無効なので実害は小さい。

03

マッチングの中身(dfs_match)

MatchTask は1つの定理・1つの束縛状態を表し、優先度付きキューで管理される。TheoremDef.patterns を先頭から満たしていくバックトラック探索で、パターンの型(Identical / Connected / DefinedBy / 汎用)ごとに専用の列挙ロジックを持つ。

Identical(v1, v2)

両方未束縛なら型で絞った代表元へ自己束縛(RETE的に定理をまたいで共有キャッシュ済み)。

Connected(child, parent)

e-graphの subobjects を辿る接続判定。両方未束縛のジョインも型だけで決まるため共有キャッシュ済み。

DefinedBy(…, result)

親が揃っていれば memo の O(1) ルックアップ、無ければその場で構成する — マッチングが副作用を持つという設計上の緊張点。

failed_paths

「この束縛状態はもう行き止まり」の記憶。定理ごとの永続マップで、タスクをまたいで共有される。無効化は型別の依存マスクで個別に判定する。

パターンのビットマスク

「まだ消費していないパターン」はu64のビットで持つ。定理のパターン列は不変なので実体は借りるだけで、分岐のたびのヒープ確保が要らない。

順序/相異の前倒し

Order/Distinctは全変数が揃うまでestimate_costが無限大を返すので最後まで選ばれない。束縛済みの範囲だけで毎回検査し、最も早い時点で枝を切る。

UCB1バンディット

シードなし全探索タスクの優先度を、定理ごとの過去の成功率+探索ボーナスで決める(--bandit、既定は無効)。未試行の定理は常に一度は試す。

定理の書き方の規約

DefinedBy は役割を宣言して書く(match_by 照合のみ / build_by その場で作る / demand_by 需要を立てる)。theorem_lint.rs がテストで、役割の食い違い・需要の供給元が無い種類・規模の上限(変数20・パターン20)・対称性・証人(その定理が発火しないと解けない問題を実際に解く)を見る。静的な検査は「必要な形の実体が図に供給されず一度も発火しない」書き換えを通してしまうので、証人だけが確実(§04 #65)。

4つのゲートウェイ

create_entity / merge_entities / link_logical_incidence / insert_memo。e-graphの生の構造を書き換える経路をここに集約し、type_generation の更新漏れを構造的に防いでいる。
