今、並行して走っている5つの方針

性質の違う作業を混ぜて着手しないための一覧(2026-09-17 時点の状態に書き直した)。数字は既定設定・44問・仕事量予算8,000,000での値。変更ごとの詳細は§04、未着手の項目は§05。

方針A射影幾何への移行と、定理の健全性型の統一は完了・射影の定理は既定
方針A 射影幾何
原則: 「本質的には普通の図形の特殊ケース」には専用のEntityTypeを作らず、標準の型と基準の実体への接続で表す。Direction→Point(無限遠直線への接続)、Circle→Conic(円周点I,Jへの接続)、Angle→Scalar(無限遠直線上の複比)の3種は撤廃済み。射影の定理5つ(複比の透視射影不変性2つ・シュタイナーの定理3つ)は全問題で既定になった(--no-projectiveで外せる)。
現状の課題: 定理の書き方の誤りは、結論のマージを数値で監査するまで見えない。線束→点(偽の等式3,525件)と共点二弦の相似(偽6件)は、どちらも一時的な監査で初めて見つかった ― 監査を常設する案が§05にある。方冪・直角三角形・二等辺三角形の定理を射影の形に移す作業は、記録上まだ手を付けていない。
方針B探索の効率と再現性32/44・決定的
方針B マッチングと探索の制御
予算は壁時計の秒ではなく仕事量(dfs_matchの呼び出し回数)で測り、数値検証とMCTSの乱数もシード固定にしたので、同じ設定なら何度流しても結果が1ステップも変わらない。失敗キャッシュは個々の失敗状態ごとの依存マスクを持つ定理単位の永続キャッシュ(鍵に無関係な束縛まで入っている問題は §05 b28、無効化が大雑把すぎて仕事量の2〜5割が歩き直しになっているのが §05 b29)、候補capは狭い値(5)から始めて手詰まりのときだけ広げる。型をまとめるときは、候補プールの混ざり方だけでなくキャッシュの無効化の粒度(angle_generation)も点検すること。
候補は cap で切る前に他の前提で絞る(§04 #55)。現状の課題: 探索が定理を試す順序に大きく左右される(登録順を変えるだけで仕事量が±15%、1問が解けたり解けなかったりする)。筋の通った並べ方はどれも登録順に勝たなかったので、順序に鈍感な探索にする方が本筋。dfs_match は貪欲な入れ子ループ結合で、候補capはその爆発に対する対症療法 ― 関係として張り直して最悪計算量最適結合で評価すれば、順序非依存もcapの不要化も同時に付いてくる(§05 b30)。未解決12問のうち5問は予算を使い切って止まる。
方針C個別の定理より、汎用の補助作図を優先需要駆動の作図が主力
方針C 補助作図
行き詰まったときの手は需要駆動の作図(補助線 → 交点 → 有向角 → もう一方の交点 → 中点 → 目標からの逆算)で、尽きたら候補capを広げる。この手順は solve・作図画面(serve)・discover の証明試行で共通のBlackboardEngine::recoverに1本化した(以前は3か所が別々に持っていて、serve だけ射影の定理を使わない・回復を打ち切るといった食い違いがあった)。需要駆動の補助線を外すと31→15問、交点を外すと31→29問で、解けている問題の約半分はこの路線が支えている。中点の需要は solve では既定で切っている(bench_2012egmop1 が落ちる)が、作図画面と discover では使う。
現状の課題: 目標から逆算する作図は一度も効いておらず、「何を作図するか」を目標側から決める手が実質無い。MCTS は既定で無効 ― 予算を仕事量にした後で測り直すと、解ける問題は1問も増えずに時間が12倍になった。
方針D定理の追加は最小限に、問題ごとの opt-in はしない診断で詰まり所を名指し済み
方針D 定理追加
定理を増やすと、無関係な問題にも試行の仕事量が乗る(射影の定理5つで平均+29%)。問題名で定理を入れる opt-in は新しい問題に効かないので使わない ― 例外は暫定の中心角の定理(CENTRAL_ANGLE_PROBLEMS)だけで、長さを橋渡しする定理は全問題一律のスイッチ(--length-theorems)にしてある。未解決の問題は、人間の証明の筋書き(SKETCH)と診断(diagnose)でどの手順で詰まっているかを名指しできるようにした。足りないのは作図より「長さ・中心・垂直二等分線」の橋渡しで、これを課税なしに既定へ入れる方法がまだ無い(§05)。
方針E無駄な作図のノイズを足しても解ける頑健性ノイズ5で32問まで回復
方針E 頑健性
ユーザー方針(2026-09-17): 問題の初期作図に、証明と無関係な作図をノイズとして加えても解けるぐらいの頑健性を目指す。難しい問題では探索そのものが大量の補助図形を作るので、最小限のきれいな図でしか解けないソルバーは難問に届かない。
判断の基準: 改善は「余計な実体があっても探索のコストと結果が変わらない」方向を優先する(定理の順序に鈍感な探索、無関係な実体で増えないコスト、図が最小であることに頼らないヒューリスティック)。特定の問題の作図の並びに合わせた調整は採らない(問題ごとの opt-in をしない方針と同じ理由)。
計測(--noise=N、§04 #50): 証明と無関係な作図をN個足して解けるかを測る。既定設定・44問で、対処前は ノイズ0: 32問 / 5個: 30問 / 10個: 28問 / 20個: 28問 ― 5個足すだけで2問落ちていた。capを広げる時機を直して(§04 #51)ノイズ5で32問・10個で29問・20個で30問まで戻した。仕事量は 50M→84M→114M→113M と増える(§04 #55 の semi-join で全体が2〜3割下がった後の値)。
既に見えている弱さ: マッチングは完全に素朴な積み直しで回っており(仕事量の100%が全体sweep由来)、ノイズを足すと sweep の回数そのものが倍増する ― bench_2022balkanmop1 で 14回→32回、仕事量 826,498→8,007,052(§05 b29)。定理の登録順を変えるだけで仕事量が±15%動き、1問が解けたり解けなかったりする(§05 b30)。作図画面で射影の定理を足すと、円の図の証明が1件減った(§04 #47)。数値チェックのコストが実体の数に比例して効く(§05)。
01

ファイル構成と入口

1つのRustバイナリ(geom_solver)に、証明・発見・退化解析・ベンチ掃引・Web配信の入口が同居している。src/mmp_core/が図形の表現(e-graph)、src/logic_core/がその上を探索する証明器、という二層が骨格。

src/main.rs

入口。未知のフラグの検出とサブコマンドの振り分け、extract-proof。

src/solve.rs

問題を1つ解くメインループ。オプションの解析(SolveOptions)→ 問題の読み込み → run_step → 目標判定(GoalChecker)→ 行き詰まったら回復(Recovery: 需要駆動の作図 → 候補capの拡大 → MCTS)、の一巡と、終了時のレポート。

src/cli.rs

オプションの一覧表とhelp/list。知らないフラグは黙って無視せずエラーにする(「変えたつもりで既定値のまま走る」事故を止めるため)。

src/mmp_core/mod.rs

EGraph・GeoEntity・Definition・EntityType・Fact・Justification。生の構造を書き換える4ゲートウェイもここ(§03)。

mmp_core/congruence.rs

apply_congruence_closureと、直線・二次曲線・交点の一意性の局所伝播。マージの実行(merge_entities_justified)もここ。

mmp_core/eval.rs

有限体上の数値評価。numeric_plausibility_check(マージ前と目標到達時の裏付け)とcached_degree(動点法の代数的次数)。

mmp_core/coords.rs

数の表現によらない評価の骨組み: 同値類の評価(同居する定義を順に試す・循環の検出)と、自由点の置き方(前提の曲線の上に置く・循環の解消・最後の検証)。有限体(eval.rs)・p進(padic_eval.rs)・実数(discover_viz.rs)の3つが共有する。

mmp_core/proof.rs

explain_identical: なぜ2つが同じ同値類に入ったかを「証明の森」から復元する。人間向けのgenerate_proofも。

mmp_core/raw_proof.rs

全マージ履歴のダンプと、その再帰的な検証(verify_identical)。extract-proofサブコマンドの実体で、合流履歴を前向き・逆向きの両方に辿る。

mmp_core/query.rs

図の状態を問い合わせる述語。merged_free_points(図の崩壊検出)はここ。

src/logic_core/theorem.rs

定理の書き方そのもの: Pattern・TheoremDef・MatchTask・TheoremBanditStats。データ構造と純粋関数だけで、探索の状態は持たない。

logic_core/prover.rs

ProverEngineの状態(e-graph・既知の事実・バンディット統計・失敗パスの永続キャッシュ)と、マッチ成立後の作図・結論の適用。

logic_core/cost.rs

「次にどのパターンを見ると安いか」(estimate_cost)と「候補が多いときどこまで絞るか」(熱capまわり)。見積もりと枝刈りの方針だけをここに集めてある。

logic_core/matcher.rs

深さ優先探索の本体(dfs_match)と、fact_typeごとの候補の展開。どれを選ぶかの方針はcost.rsに分離済み。

logic_core/blackboard.rs

探索の司令塔。タスク待ち行列を回し、行き詰まったときはrecover(需要駆動の補助作図 → 候補capの拡大)で図を伸ばす。solve・serve・discover が同じ手順を使う。

src/theorems.rs

定理の定義(23件)。get_all_theorems17件 + get_projective_theorems5件(既定で有効) + 中心角の定理1件(opt-in)。定理集合の組み立てはtheorem_setに1本化。

src/problems/

ベンチ44問。単体検証(test_*)・古典幾何・HAGeo-409由来(bench_*)。mod.rsに「目標が数値的にも本当に成り立つか」の検査を置いてある。

src/trace.rs

診断(--trace)。使った仕事のうちどれが証明に残ったかを、発火の記録と証明の遡りを突き合わせて測る(§05)。

action_space.rs / mcts.rs

補助構成の行動空間と、それを探索するMCTS。需要駆動の回復も尽きたときの最後の手段(既定は無効)。

padic.rs / padic_eval.rs

図形を退化させたときの振る舞いの解析。どの実体どうしが「一緒に潰れる」かを観測し、熱のボーナス伝播に使う(--degen-heat)。

discover*.rs

目標を持たない自由作図モード。作図を伸ばしながら非自明な一致を探し、見つけたものを証明しにいく。

serve.rs + web/

ブラウザUI。発見結果を1件ずつ流し、面白さ順に並べ替えて証明の成否まで見せる。

sweep.rs

全問題×パラメータ組み合わせの掃引。仕事量予算なので結果は機械の混み具合に左右されない。

mmp_math / mmp_calculators

法998244353の有限体演算と、各Definitionの具体的な計算。

入口(サブコマンド)は次の通り。いずれも geom_solver help に一覧が出る。

geom_solver <問題名>

証明を試す。--steps(既定800万)が本当の予算で、--time(既定600秒)は暴走時の安全弁。診断は--stats/--profile/--trace/--origins(作図の出どころ別の効き)。--audit-mergesは定理の結論を適用直前に数値で検算し、定理ごとの偽のマージを数える(探索は変えない)。行き詰まり時の手を個別に外すA/Bは--skip-recovery=line,point,second,mid,angle,target。長さを橋渡しする定理は--length-theorems。

geom_solver sweep

全44問を順に解いて成否と所要時間を集計する。--varyでパラメータを振れる。

geom_solver diagnose

問題ファイルに書いた人間の証明の筋書き(SKETCH)に沿って、補助作図と手順1..kを順に前提として与え、各手順が自力で出るかを表にする。解けない問題がどの手順で詰まるかを名指しする。

geom_solver discover

目標なしの自由作図から非自明な性質を探す。--proveで見つけた性質の証明まで試す。

geom_solver discover-degenerate

図を退化させて「一緒に潰れる」実体の組を観測する。

geom_solver extract-proof

記録したマージ履歴から、目標までの証明を再帰的に展開して監査する。

geom_solver serve

ブラウザUIを配信する。発見結果を逐次ストリームし、1件ずつ証明を試す(予算は solve と同じ仕事量)。

02

パイプライン全体

1問につき EGraph::new() → 問題ファイルによる初期条件の投入 → BlackboardEngine によるタスクキュー駆動の定理マッチング、という流れ。探索が完全に手詰まる(Stall)たびにオンデマンド作図の回復フェーズへ落ち、それも尽きれば熱capの段階拡張、最後にMCTSへ委ねる。予算は壁時計の秒ではなくdfs_matchの呼び出し回数(--steps、既定800万)で測るので、同じコード・同じ問題なら何度流しても同じ結果になる。

03

マッチングの中身(dfs_match)

MatchTask は1つの定理・1つの束縛状態を表し、優先度付きキューで管理される。TheoremDef.patterns を先頭から満たしていくバックトラック探索で、パターンの型(Identical / Connected / DefinedBy / 汎用)ごとに専用の列挙ロジックを持つ。

Identical(v1, v2)

両方未束縛なら型で絞った代表元へ自己束縛(RETE的に定理をまたいで共有キャッシュ済み)。

Connected(child, parent)

e-graphの subobjects を辿る接続判定。両方未束縛のジョインも型だけで決まるため共有キャッシュ済み。

DefinedBy(…, result)

親が揃っていれば memo の O(1) ルックアップ、無ければその場で構成する — マッチングが副作用を持つという設計上の緊張点。

failed_paths

「この束縛状態はもう行き止まり」の記憶。定理ごとの永続マップで、タスクをまたいで共有される。無効化は型別の依存マスクで個別に判定する。

パターンのビットマスク

「まだ消費していないパターン」はu64のビットで持つ。定理のパターン列は不変なので実体は借りるだけで、分岐のたびのヒープ確保が要らない。

順序/相異の前倒し

Order/Distinctは全変数が揃うまでestimate_costが無限大を返すので最後まで選ばれない。束縛済みの範囲だけで毎回検査し、最も早い時点で枝を切る。

UCB1バンディット

シードなし全探索タスクの優先度を、定理ごとの過去の成功率+探索ボーナスで決める(--bandit、既定は無効)。未試行の定理は常に一度は試す。

4つのゲートウェイ

create_entity / merge_entities / link_logical_incidence / insert_memo。e-graphの生の構造を書き換える経路をここに集約し、type_generation の更新漏れを構造的に防いでいる。
