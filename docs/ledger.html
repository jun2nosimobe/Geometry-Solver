#59関係マッチングの試作を詰めた ― 解ける問題では仕事量が3〜6割減、ただし解ける数はまだ半分試作・既定は無効
§04 #58 の試作(--generic-join)の詰まり所を1つずつ潰した。効いたのは1つだけで、それが決定的だった。
効いた: DefinedBy の親候補を、既に束縛済みの親と整合する読み方だけに絞る。 それまでは定義の親を全位置そのまま候補にしていたので、後の検査で落ちるだけの枝を大量に作っていた。定義の読み方(親の並べ替え・AnglePair の向き)を先に当てて、食い違うものを捨てる。これだけで test_spiral_similarity 10,599→1,747、cyclic_quad 25,780→857。
効かなかった案(どれも戻した/据え置き): (1) その場生成を「最優先」から「従来の見積もりと同じ重み(30)」に下げる ― cyclic_quad 3,812→25,780、orthocenter 247,601→592,437 と軒並み悪化。生成は先にやる方が良い。(2) 「その変数に決めたときだけ作る」二段階 ― 図の実体は 85→81行でほとんど減らず、仕事量もほぼ不変。(3) 需要を見積もりの段階でも記録する ― 結果は1ステップも変わらなかった(より正しいので残した)。(4) 自己束縛プールの角度除外を外す ― 解ける数は変わらず、従来の探索と同じ意味に戻した。
選抜33問での実力(基準 → --generic-join): 解けた数は 32→15 / 31→16 / 31→13 / 32→15 / 29→14 / 30→16。一方、両方が解けた問題での仕事量は −59.9% / −57.0% / −63.0% / −53.7% / −39.1% / −34.2%。9問の抜き取りでは、解けた5問すべてが既定より速い(thales 2,794→1,397、circumcenter 1,717→1,174、cyclic_quad 2,202→857、nine_point 168,041→89,444、test_spiral_similarity 19,123→1,747(−91%))。
つまり速さはもう出ている。足りないのは網羅性。
次の手がかり: 落ちる問題は有向角(AnglePair)を使うものに偏っており、miquel では定理が1つも発火しない(既定では円周角の定理17回+有向角の加法性2回)。コストではなくマッチの取りこぼしなので、AnglePair まわりの候補生成か検査に穴がある。ここを潰すのが次の一手。
既定の挙動は変えていない: 選抜33問×6設定で結果ファイルがバイト単位で一致、テスト94件通過。
#58関係マッチング(generic join)を別のマッチャとして作った ― 動くが、まだ従来より弱い試作・既定は無効
§04 #57 で「部品を1つずつ入れる道は塞がっている」と分かったので、丸ごと別のマッチャとして作った(logic_core/genjoin.rs、--generic-join)。従来の dfs_match は「パターンを1本選んで候補を出し、次のパターンへ」という入れ子ループ結合で、中間結果の爆発を熱capで抑えている。こちらは順番が逆で、次に束縛する変数を選び、その変数に触れる全パターンの候補集合を交差させてから束縛する。交差で抑えるのでcapを一切使わない。
Connected / Identical / DefinedBy / Distinct / Order を扱い、AnglePair の向き(Flip)は全変数が決まった後の検査でグループごとに決める。扱えないパターン(Not、現行の定理では未使用)を含む定理は従来の探索に回す。親がそろった DefinedBy のその場生成と、補助作図の需要の記録も移植した。
いまの実力(9問の抜き取り、既定 → --generic-join): 解けたのは 5/9。速くなったのは test_spiral_similarity 19,123→8,885(−54%)だけで、thales 2,794→9,509、circumcenter 1,717→16,297、nine_point 168,041→248,079 と軒並み重い。varignon・miquel・orthocenter・simson は予算内に解けない。まだ従来の置き換えにはならない。
分かった原因(1) capは図の成長も抑えていた: varignon で実体が 41→81行、(Auto) 由来の図形の出現が 329→2,562(8倍)。capが無いと DefinedBy のその場生成に歯止めが掛からず、図そのものが膨らむ。「その変数に決めたときだけ作る」二段階にしても 85→81行で、ほとんど減らなかった ― 生成が起きる組み合わせの数自体が多い。§04 #57 で cap を外すと解けた数が合計 −16 になった理由の一端がこれ。
分かった原因(2) 失敗キャッシュが無い: 従来の探索は定理ごとの失敗パスを持ち越すが、試作にはまだ無い。sweep のたびに一から辿り直す。
分かった原因(3) 自己束縛のプール区別が無い: 従来は Scalar を「角度」「複比」「それ以外」に分けて候補を出すが、試作は宣言型の全代表元から取る。解は落とさないが候補が増える。
既定の挙動は変えていない: フラグ無しでは従来の探索をそのまま通り、選抜33問×6設定で結果ファイルがバイト単位で一致。テスト94件通過。
次にやること(優先順): (1) その場生成に歯止めを付ける(capの代わりになる条件)、(2) 試作用の失敗キャッシュ、(3) 関係ごとの索引 ― いまは subobjects と uses の線形走査で交差しているので、候補集合が大きいと交差そのものが重い。
#57generic join の部品を1つずつ入れても効かない ― cap を外すのも変数順序も、組でも単独でも悪化した3通りとも不採用
semi-join(§04 #55・#56)で仕事量が2〜3割下がったので、候補capはもう要らなくなったのではないかと考えて測った。cap を外す・変数順序を generic join 風にする・その両方の3通りを、選抜33問×6設定で比べた。3通りとも解けた数が減った。
解けた数の合計(6設定・基準との差): --fanout-heat-cap=40(狭いcapを外す)だけで −16、--var-order(他のパターンが縛っている変数から先に束縛する)だけで −1、両方で −13。仕事量は cap を外すと +130〜440%、両方で +180〜590%。cap は外せない ― semi-join の後でも実際に効いている。
変数順序は振れ幅が異常に大きい: 単独での仕事量の変化は 設定ごとに −17.7% / −0.2% / +9.1% / +15.6% / +24.2% / +388.1%。解ける問題も入れ替わる(ノイズ10 で bench_2018silkroadp1 と bench_2022balkanmop1 が解けるようになる一方、bench_2012egmop1 と simson を落とす)。
埋もれている良い面: --var-order はノイズ5 で 33/33 ― 選抜の全問が解けたのはこれが初めて。
6問の抜き取りでは逆に見えた: 抜き取りでは「両方」がいちばん良く見え(bench_2018chnwesternmop5 ノイズ10 が 0→1、801,242ステップ)、33問で測ると −13 だった。抜き取りで方向を決めてはいけないという例。
結論: いまの「パターンを選んで候補を出し、熱の順に cap で切る」探索は、よく釣り合った局所最適になっている。generic join の部品(索引・交差・変数順序・capなし)は互いに前提し合っているので、1つずつ入れると必ずどれかが足を引っ張る。§05 b30 は別のマッチャとして丸ごと作るしかない、というのが3回の計測(#56 と今回)で確定した。--var-order はフラグとして残した(既定は無効)。
#56semi-join を DefinedBy にも広げる ― ついでに「変数の選び方」を generic join 風に変えたら proof が落ちた57b09e9
§04 #55 の semi-join は Connected と Identical の候補にしか掛かっておらず、DefinedBy の候補だけ素通しだった。2か所に足した: (1) 結果が未束縛なら、定義を展開する前に候補を絞る(型の全代表元を舐める分岐ではここで落ちる数がそのまま効く)。(2) 定義から取れた親の組も、熱と次数で並べ替える前に絞る(並べ替えは候補ごとに次数を測るので重い)。
実測(選抜33問、semi-join 既定との差分): 全設定で −0.5〜−1.0%、解けた数は不変。全44問でも解けた数はどの設定でも不変で、#55 以前からの累計では 既定 −24.0% / 長さ+中心角+中点 −34.0% / skip-recovery −29.7% / ノイズ5 −31.1% / ノイズ10 −33.3% / ノイズ20 −27.1%。テスト94件通過。
試して外したこと ― generic join の「変数の選び方」: 見積もり(estimate_cost)はパターン1本だけを見て候補数を測るので、他のパターンがその変数をきつく縛っていても高く見える。そこで「相手が束縛済みのパターンが生成できる候補数」を集めて上界とし、見積もりをその上界で置き換えた(= 交差後にいちばん小さくなる変数から束縛する)。
結果は振れ幅が大きく、テストが1件落ちた(serve::tests::a_missing_midpoint_no_longer_blocks_the_proof: 中点連結定理の形が証明できなくなった)。1問ごとでは bench_2022balkanmop1 ノイズ10 が 0→1 で解けるようになる一方、bench_2018chnwesternmop5 が 1→0、bench_2005ctstp1 ノイズ10 が 428,732→3,812,262(9倍)。
理由: 「いちばん縛られている変数から束縛する」は完全な探索なら正しいが、cap があるせいで「どの候補が切り捨てられるか」まで変わってしまう。cap を外さないうちは変数順序を触っても良し悪しが安定しない。
分かった順序: b30 の残り(パターンではなく変数を選び、全パターンの候補集合を交差させて cap 自体を要らなくする)を先にやること。変数順序の最適化はその後でないと測れない。
#55候補を cap で切る前に、残っている他のパターンで先に絞る ― 仕事量が全設定で2〜3割減9d174f5
§05 b30(入れ子ループ結合をやめて関係マッチングにする)の第一歩。
それまでの順番: 候補を熱の降順に並べて cap(自己束縛などは5、通常は40)で切り、残ったものを1つずつ束縛してから、深いところで他のパターンに当てて落とす。つまり「他の前提も満たす正しい候補」が、当てられる前に cap の外に落ちることがあった。
変えた順番: 先に他のパターンで絞り、残ったものを cap で切る。使うのは、まだ残っているパターンのうち相手が束縛済みで候補1つを見るだけで判定できる3種類 ― Connected(その図形と接続しているか)・Identical(同じ代表元か)・Distinct(異なるか)。ここで落ちる候補はどのみち後で同じパターンに当たって落ちるので、解は1つも減らない。効くのは cap との順番だけ。関係の言葉でいう semi-join reduction にあたる。
semi-join が読む相手の型は、失敗キャッシュの依存ビットにも足してある。
実測(全44問 × 6設定、基準 → 既定): 解けた数はどの設定でも不変(32 / 31 / 31 / 32 / 29 / 30)。仕事量は 既定 −23.4%、長さ+中心角+中点 −33.3%、skip-recovery −29.1%、ノイズ5 −30.6%、ノイズ10 −32.6%、ノイズ20 −26.7%。1問ごとでは bench_2005ctstp1 742,344→401,236(−46%)、nine_point_full 807,600→603,665、test_spiral_similarity 27,462→19,481。
配線の確認: 既定有効の結果が --semijoin を明示したときと完全一致し、--no-semijoin が変更前と6設定すべてで1ステップも違わず一致した。テスト94件通過。
まだ generic join ではない: これは「1つのパターンから候補を出し、他のパターンで絞る」形。本来の generic join は「パターンではなく変数を選び、その変数に触れる全パターンの候補集合を交差させる」もので、そこまで行くと cap 自体が要らなくなる可能性がある。残りは §05 b30。
#54半素朴評価を追いかけたら、本丸は「失敗キャッシュを捨てすぎていること」だった ― 仕事量の半分が歩き直し358e3fa · 2案とも不発
§05 b29(全体sweepを半素朴評価にする)の着手条件は「どの定理の sweep を省けるか決めること」だった。やってみると、その道は塞がっていて、代わりにもっと大きな穴が見つかった。
計測を3つ足した(--profile のみに出る。探索の挙動は全44問×6設定で変わらないことを確認済み): 失敗キャッシュの当たり/無駄になった当たりの数、型世代を上げた理由の内訳、失敗を記録したときの依存マスクの幅。
分かったこと: dfs_match の呼び出しのうち、キャッシュに当たったのに型世代が変わっていて使えなかったものが、bench_2022balkanmop1 ノイズ10 で 51.3%(当たり 9.9% の5倍)。ノイズ無しでも 20.2%、bench_2005ctstp1 で 38.7%。探索の2〜5割が、すでに失敗と分かっている枝の歩き直しに消えている。
無効化の原因は接続関係の追加が57〜59%(うち Point が約半分)、memo登録 18〜22%、実体の生成 12〜13%、マージ 8〜9%。
2案とも不発: (1) 型世代を「候補集合(生成・memo・マージ)」と「接続関係(接続・マージ)」に分けて8ビットにした ― 接続関係が6割を占めるので効くと見込んだが、仕事量は −0.05%(bench_2005ctstp1 742,344→741,964)。理由は3つ目の計測で分かった: 依存マスクは1〜3ビットで98%と元々細く、問題は細さではなく、1本のビットが「その型のどこかで何かが起きた」という全体の通し番号であること。link(Point) だけで数千回上がるので、1ビットしか立っていないエントリも普通に死ぬ。(2) 「前回走査し切ってから読む型も cap も変わっていない定理は sweep で積まない」 ― 省けたタスクは全設定で0件。sweep と sweep のあいだに何百ものタスクが結論を適用するので、4つの型世代は必ず全部動く。
結論: 残る軸は「どの型か」ではなく「どの実体か」。枝が実際に読んだ代表元を覚えて、それが変わったときだけ捨てる形が要る。これは索引を持つ関係マッチング(§05 b30)と同じ構造を要求するので、b30 を先にやるべき根拠が1つ増えた。2案のコードは戻し、計測だけ残した。
#53定理証明支援系まわりの技術を当てはめて棚卸しし、失敗キャッシュの鍵を核に絞る案を測った既定にはしない
「Lean のような定理証明支援系の技術がここに応用できるか」を検討した。Lean 本体(依存型・カーネル・tactic 言語)から取れるものはほとんど無い ― 向こうの難所は人が書いた証明項の elaborate と検査で、こちらは地の事実からの飽和なので問題が違う。一方、隣にある道具立て(SMT の E-matching、Datalog / egglog、飽和証明器、Sledgehammer の関連度フィルタ)は今の課題にほぼ一対一で対応する。棚卸しの結果を §05 b28〜b32 に入れた。
そのうちいちばん安く試せる b28 を実装して測った: 失敗キャッシュの鍵(state_signature)は束縛を全部入れて作っていたが、失敗の理由はたいてい数個の変数しか使っていない。鍵を「残っているパターンが実際に見る変数」だけに絞れば(--nogood-core)、無関係な変数の値の数だけ同じ失敗を作り直すのを避けられる ― SAT/SMT の nogood learning にあたる。
結果(選抜33問、基準 → --nogood-core): 仕事量は全設定で下がる(既定 −1.5%、extras −15.1%、skip −9.4%、ノイズ5 −4.2%、ノイズ10 −5.5%、ノイズ20 −5.3%)が、解けた数は合計 −3(extras・skip・ノイズ5 で bench_2012egmop1、ノイズ20 で bench_2018chnwesternmop5 を落とし、ノイズ10 で bench_2011balkanmop1 を得る)。既定にはせず、フラグとして残した。
落ちる仕組み: 刈りすぎではなく「予算の縁にいる問題が押し出される」。bench_2012egmop1 は --central-angle だけなら解けるが 1,496,033 → 2,083,867 ステップかかるようになり、extras/skip/ノイズ5 の --steps=1500000 を超える。
試して外したこと: 鍵を核に絞るなら候補の並べ替えも核だけで決めるべきと考えて DefinedBy の並べ替えの熱を核に限ったが、6設定すべてで1ステップも変わらなかったので戻した。
ついでに測れたこと(b29 の前提): 既定では探索の仕事量の 100% が全体sweep由来のタスクで、シード済みタスクの消費は 0。ノイズを足すと sweep の回数が倍増する(bench_2022balkanmop1 で 14回→32回、仕事量 826,498→8,007,052)。マッチングは完全に素朴な積み直しで回っている。

#51候補capを広げるのが遅すぎた ― 行き詰まり2回ごとに需要作図より先に広げる0957282
